Every decision in this project is written down here with its date. Interview answers, recorded assumptions, design panel choices and open questions all live in this one file so that nobody has to reconstruct why the code is the way it is.

Rules for this file:

- Every entry carries the date it was made.
- Entries are appended, never rewritten. If a decision is reversed, add a new dated entry that says so and points at the one it replaces.
- A decision that only Jonny can make is listed under "Open questions" with a proposed default until he answers; the default is what the code does in the meantime.

## Design decisions (2026-10-13, design panel)

Taken from the final design produced by the design panel (three independent designs, three judges, one synthesis, two sceptics, one repair pass). One bullet each with the reason.

- **Integration plus ROS2 package, not an add-on.** Every living HA-to-ROS2 precedent is a purpose-built ROS node publishing MQTT discovery; a ROS2 runtime inside an add-on needs host networking and couples HA to the arm's distro, and an add-on cannot create HA entities or typed services by itself.
- **One process per robot.** A stalled or crashed executor affects only its own robot, and a duplicate robot id collides visibly on the broker because the MQTT client id is derived from the robot id.
- **MQTT 5 on both sides with `clean_start` true.** Message expiry on replies needs MQTT 5, HA already requires an MQTT 5 broker since 2026.6, and a clean start means a restarted node never drains a broker-queued backlog of motion commands.
- **Replies retained with expiry.** HA does not wait for SUBACK (0.5 s subscribe debounce), so a fast non-retained ack can be missed; retained replies with an expiry of 120 s (ack) or 300 s (result) stay available long enough without staying for ever.
- **Replies routed by id alone; session only detects a node restart.** Filtering replies by session discarded genuine results published after a node restart; the per-command session stored on the HA side is used only to mark a command `lost` when the node that accepted it is gone.
- **Cancel is ack-terminal.** A cancel command's `accepted` ack is its terminal outcome and the cancelled task's own result arrives under the task's id, so HA never waits for a result the contract does not promise.
- **One active motion task per robot, `rejected_busy`, no queue.** Matches Q17 (discrete states only) and keeps the state machine small; queueing or pre-emption is on the post-release track if a real executor needs it.
- **HMAC optional and off by default (Q15).** Jonny chose to reuse the existing MQTT user for testing, so the shared secret is an opt-in layer that adopters switch on with one option on each side.
- **Authorisation in the node, because the stock Mosquitto add-on does not enforce ACLs.** With home-assistant/addons issue #4571 open, any authenticated client can publish commands, so the node itself applies the UUID id check, allowlist, freshness window, persisted dedupe, retained drop and the optional HMAC.
- **Watchdog mode `none` by default (Q16).** HA going away must not affect the arms; the heartbeat is kept as an informational `ha_link` state, and `inhibit_new` and `stop_and_hold` are a parameter for adopters who want them.
- **No thread-pool guard around executor calls.** Plugin methods run on the node's main thread; a plugin that blocks stalls only its own robot, the heartbeat stops and HA shows `problem` within about 6 s, which was judged simpler and safer than a worker pool that could leave a half-run call behind.
- **ament_copyright not used; SPDX headers with `scripts/check_spdx.py` instead.** ament_copyright cannot read SPDX headers (verified: it requires a `Copyright YYYY Holder` line followed by the full Apache notice), which contradicts Q18, so one script is the single header gate for the whole repository.
- **probatio, not voluptuous, on the HA side.** At HA Core 2026.10.1 voluptuous is not installed (it exists only as a `sys.modules` alias) and core bans the import, so the integration imports probatio directly and annotates schemas with `VolSchemaType`.
- **Copyright holder written as "ha-ros2-bridge contributors" pending Jonny's say.** A neutral holder keeps the headers correct for outside contributors and avoids putting a personal name in every file without asking; Jonny can change it with one find-and-replace.
- **Buttons, not selects, for motion.** Selecting an item in a select entity must never start an arm moving; a button press is an explicit act, and parameterised tasks go through the `send_task` service.
- **Discrete state only (Q17).** `idle`, `busy`, `error` plus events; no joint telemetry, so no recorder exclusions and no high-rate MQTT traffic; extra telemetry can be added later as optional non-retained topics.
- **Row 7's "or a select" is superseded by "Buttons, not selects, for motion" (2026-10-13).** The interview cell keeps the plan's wording; the design records why a select entity must never start motion.
- **Row 13's WSL2 and throwaway HA container options were superseded by Q14 (2026-10-13).** Q14 chose the live HA as the HA side and ROS2 Jazzy in Docker on the development PC, with the safeguards listed in row 14, so row 13's "Jonny's live HA instance is not a test bed" is superseded as well.
- **Row 12's open Isaac check was closed by research 2 and Q20 (2026-10-13).** Isaac Sim 6.1.0's ROS 2 bridge supports Jazzy, Isaac Sim cannot run on the development PC, and Isaac runs only at the other site, so Isaac testing is deferred (row 20).
- **Row 19's default prefix is written `ros2_bridge`, without the plan's trailing slash (2026-10-13).** The contract's prefix convention forbids a leading or trailing slash, so the configured default is `ros2_bridge`; the interview cell keeps the plan's `ros2_bridge/`.

## Phase 1 decisions (2026-10-13, ROS node core)

Choices made while implementing the rclpy-free core of the ROS 2 node (`protocol.py`, `authoriser.py`, `dedupe_store.py`, `task_manager.py`, `watchdog.py`, `sensor_mirror.py`, `executors/base.py`, `executors/fake.py`). One bullet each, with the reason as the code's own docstrings give it; the docstrings are the fuller word.

- **Dedupe runs the moment the id is known, before the schema, signature and freshness checks (2026-10-13).** The lookup follows `decode_command` directly, for a decoded command and for a replyable decode error alike. Reason: the contract promises one distinct ack per id, and if any later check could still produce a different ack for a known id, an unsigned or deliberately broken replay of an accepted command would overwrite the retained `accepted` ack on the broker, and a redelivery could downgrade it to `rejected_stale`; republishing the stored bytes gives a replayer nothing it could not already read from the retained topic.
- **Two-phase ack (2026-10-13).** `Authoriser.handle` returns an `Ack`; the task manager calls `commit()` or `reject()` exactly once, and that is where the dedupe write and the counters happen. Reason: an ack that passed every check in the authoriser is not yet final, because `executor.start` may still refuse or raise (`rejected_executor`) and a cancel may name no running task (`rejected_no_such_task`); rejections decided in the authoriser are recorded at once.
- **Freshness `now` and `received_at` are taken when `handle()` runs on the main thread, not at paho receive time (2026-10-13).** Reason: so a stalled node never acts on an intent that aged in its own queue.
- **One distinct ack per id, first ack wins in the store (2026-10-13).** A duplicate republishes the stored bytes with the stored retain flag. Reason: the dedupe lookup runs before anything that could produce a second ack, so remembering an id twice only ever replaces an entry whose bytes turned out to be unreadable; the retain decision travels with the entry so that a rejection published non-retained because `reply.retained_rejections_per_minute` was exhausted stays non-retained when it is republished, and a replay cannot defeat the budget.
- **The timeout clamp applies to the announced default as well as to a command-supplied value (2026-10-13).** Effective `timeout_s` is `min(requested or announced, task_timeout_cap_s)`; `resolve_request` in `authoriser.py` is the single implementation, and `Authoriser.set_tasks` clamps the announced catalogue to the same cap. Reason: this is the one place the effective timeout is decided, the task manager arms its deadline from the request it is handed and never recomputes it, and the catalogue the node announces names the timeout the node will enforce, so Home Assistant's result deadline (announced value plus margin) cannot outlive the node's timer.
- **Step 9 gating has one implementation (2026-10-13).** `gate_motion` in `authoriser.py` checks busy before error, then inhibited; `control` and `query` tasks never consult it. Reason: the authoriser applies it to its state view and `TaskManager.motion_rejection` applies it to the manager's own state, so the ack code and reason never depend on which module answered.
- **Acks are returned, never published, by `TaskManager.start` and `TaskManager.cancel` (2026-10-13).** The authoriser's caller publishes every ack. Reason: a motion task's `busy` state is published inside `start`, so it may precede the ack on the wire; HA matches replies by id and does not depend on the order across topics.
- **State is published on observable change only; every change bumps `seq`; the node must call `publish_state` on (re)connect (2026-10-13).** Reason: the manager starts by assuming the world knows the initial idle state, so only a change publishes one retained state, and the node publishes the first retained state explicitly when it connects.
- **Forced finish rule (2026-10-13).** A timeout whose cancel returned normally gives `aborted/timeout`; a cancel that raised, or a cancel not caused by the timeout that produced nothing within the grace, gives `aborted/executor_unresponsive`; the robot stays in `error` until `ctx.clear_error()`. Reason: a task that runs past its timeout is asked to cancel and, after `cancel_grace_s` without a finish, is forced, and every forced finish puts the robot into `error` until the executor calls `clear_error`.
- **Every task kind gets a deadline timer; only motion occupies the slot (2026-10-13).** Reason: control and query tasks never touch the motion slot, but the contract promises exactly one result per accepted task, so a control or query task that never finishes is forced like any other.
- **`stop_and_hold` finishes the motion task with `cancelled/inhibited` as an override and does not put the robot into error (2026-10-13).** Reason: this is a deliberate action, and `inhibited` is what keeps new motion out; whatever the executor reports for the task later is dropped.
- **`set_paused(True)` with no active motion task is ignored with a warning; `paused` clears when the slot is released; pause freezes only the deadline timer (2026-10-13).** Reason: `set_paused(True)` keeps the robot `busy` with `paused: true` and freezes the active motion task's timeout clock by cancelling its timer and storing the remaining seconds, and `set_paused(False)` re-arms exactly that remainder.
- **Result `data` is round-tripped through the wire encoding (2026-10-13).** Unserialisable data is replaced by `{"unserialisable": repr}` truncated to 512 characters. Reason: the contract promises exactly one result per accepted task, and the manager publishes it exactly once with no retry, so the payload must encode first time.
- **Sensor mirror envelope (2026-10-13).** The keys are always present in the order `topic`, `payload`, `encoding`, `retain`, `source_available`, `rx_ts_ms`; `encoding` is `utf-8` or `base64`; availability sibling messages are themselves emitted as envelopes; an empty availability payload resets the tracked state to unknown. Reason: the payload travels unchanged so a Zigbee2MQTT event reaches ROS 2 at the same time as it reaches Home Assistant, an availability message is mirrored too so a consumer learns that a sensor went offline without waiting for a data message that will not come, and an empty retained publish clears the sibling, back to unknown.
- **Mirror configuration errors are fail-fast (2026-10-13).** `TypeError` for a wrong type and `ValueError` for a bad value, raised at construction. Reason: a bad filter is an operator error that should stop the node at start-up rather than silence a sensor path; nothing raises on an inbound message, which is logged and counted instead.

## Phase 2 decisions (2026-10-13, ROS packaging and rig)

Choices made while implementing the rclpy and paho layers of the ROS 2 node (`mqtt_link.py`, `ros_adapters.py`, `parameters.py`, `bridge_node.py`), the test doubles (`test/fakes.py`, `test/conftest.py`) and the Docker rig (`tools/`). One bullet each, with the reason as the code's own docstrings and comments give it; the docstrings are the fuller word.

- **Timers and the monotonic clock run on one rclpy `STEADY_TIME` clock per node, never the ROS time clock (2026-10-13).** `new_steady_clock` in `ros_adapters.py` makes it, the node shares it with its `RclpyClock`, its `RclpyScheduler` and every periodic timer, and `RclpyClock` and `RclpyScheduler` refuse a clock that is not `STEADY_TIME`. Reason: the node's own clock is `ROS_TIME`, which with sim time off is the system wall clock, so an NTP step would shorten or lengthen every task deadline, cancel grace, heartbeat and watchdog interval, which the core's `Clock` contract forbids; the recorded trade-off is that `use_sim_time` no longer stretches deadlines or rate limits, which run on real elapsed time even when the rest of the graph runs on simulated time.
- **One-shot timers are rclpy periodic timers whose callback cancels and destroys the timer on its first line (2026-10-13).** `RclpyOneShot` creates the timer with the delay as its period, and `remaining_s` is read from the same steady clock, so pause and resume re-arm exactly the seconds that were left. Reason: rclpy Jazzy has no one-shot timer (verified: `Timer` offers cancel, reset and a period, nothing single-fire), and disposing of the timer before the callable runs means it can never fire twice.
- **Main-thread posting is a deque drained by a `GuardCondition` callback on the executor thread (2026-10-13).** `MainThreadPost.post(fn)` appends the closure and triggers the guard from any thread; the guard's callback drains the deque in posting order, and a closure that raises is logged and counted, never propagated. Reason: rcl documents guard-condition triggering as thread-safe, so the task manager's `TaskHandle` and `BridgeContext` calls from executor threads and rclpy callbacks all land on the `SingleThreadedExecutor` thread, which is the "main thread" the core's docstrings refer to, and one bad closure cannot stop the ones behind it.
- **The secrets `mqtt.password` and `command.secret` are declared, read once and then undeclared, with a WARN naming the environment variable when a value came from the params file (2026-10-13).** `ROS2_HA_BRIDGE_MQTT_PASSWORD` and `ROS2_HA_BRIDGE_COMMAND_SECRET` are the recommended route; the two secrets are the only parameters not declared read-only, because rclpy refuses to undeclare a read-only parameter; `MqttSettings`, `CommandSettings` and `MqttLinkConfig` mark the secret fields `repr=False`, and `describe_settings` masks them in the start-up log. Reason: a declared parameter sits in the parameter server, where any participant on the DDS domain could read it with `ros2 param get`, and a logged or raised settings object must never show a secret.
- **A QoS 1 publish while disconnected is logged at DEBUG and not counted as a publish error; a QoS 0 publish while disconnected remains a counted loss (2026-10-13).** The node also withholds a state change while disconnected, because the retained state is republished in full on every connect. Reason: paho answers `MQTT_ERR_NO_CONN` for a QoS 1 publish while disconnected but keeps the message and sends it after the next CONNACK, so it is not a failure; a QoS 0 message is lost.
- **Session takeover (reason code 142) doubles the reconnect minimum per takeover; the configured minimum is restored only once the ten-minute takeover window is quiet, not on every successful connect (2026-10-13).** After `mqtt.takeover_exit_after` takeovers within the window the node exits non-zero so the launch file's `respawn_max_retries` can stop the flapping. Reason: a takeover means another bridge process is running with the same `robot.id`, and paho resets its own backoff after each successful CONNACK, so the minimum must be raised in the link and kept raised while any takeover is inside the window, or two flapping nodes would keep hammering the broker.
- **The entrypoint sources the ROS 2 and colcon setup scripts without `nounset` and enables `set -u` only afterwards (2026-10-13).** Reason: the setup scripts test bare `$COLCON_TRACE`, `$COLCON_CURRENT_PREFIX` and `$AMENT_TRACE_SETUP_FILES`, which are unset in a fresh container, so sourcing them under `set -u` aborts the entrypoint before any sub-command runs; the official `ros_entrypoint.sh` uses `set -e` alone for the same reason.
- **The import-hygiene tests run the import in a fresh interpreter (2026-10-13).** The seven phase 1 tests that prove the core modules import neither rclpy nor paho now call `assert_imports_without` in `test/conftest.py`, which imports the module in a subprocess, instead of asserting on the whole process's `sys.modules`; the phase 2 tests for `parameters.py` (neither), `mqtt_link.py` (no rclpy, paho expected) and `ros_adapters.py` (no rclpy) use the same helper. Reason: under `colcon test` in the Jazzy container the test process already holds rclpy, because `pytest.importorskip('rclpy')` runs at collection in the rclpy-dependent test modules, and the link tests hold paho, so the process's own `sys.modules` says nothing about the module under test.
- **`test/fakes.py` was extended additively for phase 2 (2026-10-13).** Retain As Published per subscription, session takeover with reason code 142 as a server-sent DISCONNECT that publishes the will, and the drain helpers (`wait_idle`, `wait_for_deliveries`) were added; `FakeClock` and `FakeScheduler` are untouched and no phase 1 behaviour changed. Reason: `FakeBroker` and `FakeMqttClient` model the subset of paho-mqtt 2.x that the phase 2 `mqtt_link` needs, and the phase 1 tests that run on the fakes must keep passing as they are.
- **Re-announce on catalogue change is not implemented; recorded as a post-release item (2026-10-13).** The node reads `executor.tasks()` once in `_catalogue` at start-up, and the announce it publishes on connect and on HA's birth carries that catalogue. Reason: the executor interface (`TaskExecutor.tasks`) has no signal for a changed catalogue, so there is nothing for the node to react to; see open question (g).
- **The Docker rig never uses host networking (2026-10-13).** Every service sits on one user-defined bridge network, `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` keeps each node's DDS discovery inside its own container, the only traffic that leaves the network is MQTT over TCP to the configured broker, and the `local-broker` profile (anonymous Mosquitto, not published on the host) exists for CI and offline use. Reason: two fake arms must never see each other over DDS and nothing from the rig may reach the LAN; the defaults in `compose.yaml` and the image are placeholders, and nothing there names a host, a user or a secret.

## Open questions for Jonny (asked one at a time)

Each is asked on its own, in plain chat with numbered options, as the working agreement requires. Until answered, the proposed default is what the code and documents do.

1. **(a) Licence carriers.** `manifest.json` has no licence key, so Q18's literal wording ("licence string in manifest.json") cannot be met there. Proposed default: the licence lives in `LICENSE`, the SPDX headers, `package.xml` and `setup.py`, and ament_copyright is dropped in favour of `scripts/check_spdx.py` (it cannot read SPDX headers). Status: open.
2. **(b) When to create the public GitHub repository.** Creating it is an outward-facing action. Proposed default: not before the phase 0 scaffold has been reviewed locally; creation, the codeowner handle, release tags and the HACS listing each wait for an explicit go-ahead. Status: open.
3. **(c) `hold_on_startup`.** Whether the node should call the executor's `stop_and_hold` once at start-up before accepting commands. Proposed default: off. Status: open.
4. **(d) Missing ack.** Whether a command that never receives an ack should be reported as its own event type (`unknown`) or as `timeout` with `code: no_ack`. Proposed default: `timeout` with `code: no_ack`, documented as "outcome unknown", not as failure. Status: open.
5. **(e) Redaction of the research JSON files.** Two of the verbatim workflow outputs in `docs/research/` carried the development account's local repository path once each; on 2026-10-13 the token was replaced by `<repo root>` so that no account name ships in the public repository, and `docs/research/README.md` says so. Proposed default: keep the redaction. Alternative: restore the token with one find-and-replace and amend the README. Status: open.
6. **(f) Rejections for an id that already holds a stored accepted ack.** Whether a malformed or unauthorised rejection for an id that already holds a stored `accepted` ack should be published at all. The code republishes the stored accepted ack instead, so such a rejection is never published and the retained `accepted` ack is never overwritten. Proposed default: keep as implemented. Status: open.
7. **(g) Signalling a changed task catalogue.** The executor interface has no way to tell the node that its task catalogue changed, so the catalogue is read once at start-up and re-announce on change is not implemented (see Phase 2 decisions). Proposed default: add an optional callback to the executor interface in a later release. Status: open.
