# Failure modes

This page is the full form of the failure table that `docs/mqtt-contract.md` summarises: every failure the code handles today, what the mechanism is, what Home Assistant shows, and the tests that prove it. It is enforced: `scripts/check_failure_modes.py` parses the table, resolves every `path::test_name` in the last column to a real `def` in a real file, and `contract.yml` fails when one is missing. A row whose cell says `no test yet` is allowed so that the gap is written down rather than hidden; those rows are repeated under "Rows without a test" at the end, and the script requires that too.

Conventions:

- Paths are relative to the repository root. `tests/` is the Home Assistant suite (`ha.yml`, Linux, Python 3.14). `ros2/ros2_ha_bridge/test/` is the ROS 2 suite; its `test_bridge_node.py` needs rclpy and runs under `colcon test` in the Jazzy container (`ros2.yml`), while the rest runs on any Python 3.12 or newer.
- The script checks that each named test exists, not that it passes; the two workflows above run the suites.
- Parameter names are the ROS 2 node's (`watchdog.mode`, `reply.ack_expiry_s`) or the integration's options (`heartbeat_unavailable_after_s`, `max_pending_per_robot`); defaults are in brackets. `docs/configuration.md` lists them all.
- "Counter" means a field of the node's heartbeat `counters` object (shown per robot in the diagnostics download) or of the integration's own `hub.counters`.
- To add a row, name at least one existing test, or write `no test yet` and add the row to the final section in the same change.

## Rows without a test

These rows say `no test yet` above. The behaviour is in the code and is described from it; a test is owed for each and the checker reports them on every run so they are not forgotten.

- Empty retained payload on availability, state, ack or result (an expired or cleared retained message): `hub.py` handles the four empty-payload cases, but no test in `tests/` fires an empty payload on those topics (the tombstone tests cover the announce topic only).
- Ack and result subscriptions never confirmed within `READY_TIMEOUT_S` (10 s): the `not_ready` behaviour before confirmation is tested (previous row); the 10 s fallback in `BridgeHub._on_ready_timeout` that logs a warning and continues is not.

## Not handled

Failures the code does not defend against, by design or because the work is on a later track. `docs/security.md` has the security side of this list.

- Two Home Assistant instances on one broker: both heartbeat and both can command; `instance_id` makes it visible in diagnostics but nothing prevents it.
- A trusted client that holds the shared secret publishing valid, fresh, allowlisted commands: indistinguishable from Home Assistant by design.
- A compromised broker: it can drop, delay or replay within the freshness window, forge replies, and publish tombstones; replies are not signed.
- Executor catalogue changes at run time: the catalogue is read once at start-up (open question (g) in `docs/decisions.md`).
- An MQTT 3.1.1-only broker on the ROS side: retained replies would never expire and a live retained command would arrive with RETAIN 0, caught only by freshness and by the reconnect-time drop; Home Assistant's own client already requires MQTT 5.
- A result retained and expired (`reply.result_expiry_s`, 300 s) before Home Assistant came back from a long outage: reported as `timeout` (`no_result`) or `lost`, with `late_result` if it arrives after all.
- The duplicate-id heuristics also trip on a single node in a crash loop; the repair text says so, because both deserve attention.
